# WikiTip → KLifeMap 유입 설계

작성 2026-08-01 · 지시: 「워키팁에서 K라이프맵을 붐업시켜야 해」
관련: `한류매체-동남아-시장조사.md` · `사업전략-데이터제공업.md`

---

## 0. 왜 이 조합이 되는가 — 세 가지가 맞물린다

**① 시장이 맞다.** 동남아는 운세·점술 소비가 일상에 들어와 있다. 태국·베트남은 택일과
점성이 결혼·이사·개업에 실제로 쓰이고, 인도네시아·필리핀도 마찬가지다.
**그런 시장에서 「한국식 사주」는 미신 상품이 아니라 한류 상품이다.**
방탄 굿즈를 사는 사람이 K-사주도 본다.

**② 유입 원가가 0이다.** KLifeMap 이 동남아에서 유료 전환을 만들려면 그 독자를 데려와야
하는데, 광고로 사면 비싸다. **WikiTip 은 기사로 모은다.**

**③ 파는 물건이 이미 있다.** KLifeMap 은 결제 구조가 이미 돌아가는 유일한 사업이고,
**B2B 판정 엔진 API 까지 만들어 뒀다**(`apiBusiness.js` — 「화면이 아니라 판정값을 파는 사업」).
WikiTip 이 그 API 의 첫 고객이 되면 두 가지가 동시에 증명된다 —
API 가 실제로 남의 서비스에 물린다는 것, 그리고 해외 유입이 전환된다는 것.

```
WikiTip (동남아 한류 독자, 원가 0)
     ↓  판정 엔진 API 호출
     ↓  영문 결과를 기사·도구 안에서 보여준다
KLifeMap (전체 풀이는 여기서 · 결제)
```

## 1. 무엇으로 끌어오는가 — 궁합이 압도적이다

**K-pop 팬덤이 이미 하고 있는 놀이가 궁합이다.** 서양 팬덤은 별자리(astrology)로 멤버
궁합을 따진다. 「이 조합이 왜 잘 맞는가」는 이미 수요가 검증된 콘텐츠 포맷이다.

그 자리에 **한국식 궁합**을 넣는다. KLifeMap 에 `gunghapEngine.js` 가 이미 있다.

| 후크 (유입) | 전환 (KLifeMap) |
|---|---|
| **아이돌 조합 궁합** — 팬덤이 가장 많이 소비하는 포맷 | 「Your own chart」 |
| **당신과 최애의 궁합** — 독자 참여형 | 전체 풀이 결제 |
| 한국 띠·연도 해설 | 신년 운세 |
| **결혼·이사 택일** — 동남아에서 실제로 쓰는 관습 | 택일 서비스 |
| 데뷔일·컴백일에 붙는 의미 | — |

### ⚠ 다만 정확히 해 둘 것 두 가지

**(가) 사주는 태어난 시(時)가 필요한데, 아이돌 출생시각은 공개돼 있지 않다.**
생년월일만으로는 사주 네 기둥 중 하나(시주)를 못 세운다. 이걸 숨기고 「완전한 사주」인 척하면
사주를 아는 독자에게 바로 들통난다.

→ **표기를 정직하게 한다.** "based on birth date only; the birth hour is not public, so the
hour pillar is omitted." 오히려 이 문장이 「이 매체는 아는 사람이 만든다」는 신호가 된다.
독자 본인 도구에서는 시각을 입력받으므로 온전한 풀이가 나온다 — **그 차이가 곧 전환 동기다.**

**(나) 실존 인물에 대한 단정은 하지 않는다.**
「이 사람은 이런 성격이다」가 아니라 「이 조합은 전통적으로 이렇게 읽힌다」로 쓴다.
엔터테인먼트임을 명시한다. 운세 콘텐츠는 재미로 소비되지만, 실명 인물에 대한 단정은
매체 신뢰와 법적 위험 양쪽에 걸린다.

## 2. 전환 경로 — 세 층

```
① 기사 안 —  아이돌 궁합 기사 끝에 「Try your own」
② 도구 —     /tools/compatibility 에서 직접 입력해 맛보기 결과
③ 결제 —     전체 풀이는 KLifeMap 으로 (여기서 돈이 돈다)
```

**핵심은 ② 다.** 기사에서 바로 KLifeMap 으로 보내면 이탈한다. 낯선 사이트에 생년월일을
입력하라는 요구가 첫 접점이 되기 때문이다.
**WikiTip 안에서 한 번 써 보게 하고**, 결과가 흥미로울 때 넘긴다.

### 맛보기와 전체 풀이를 어떻게 가르는가

| WikiTip (무료 맛보기) | KLifeMap (유료 전체) |
|---|---|
| 궁합 라벨 + 한 문단 해설 | 오행·십신 상세, 시기별 흐름 |
| 두 사람 | 가족·팀 단위 |
| 저장 없음 | 기록·재조회 |

**맛보기가 시시하면 아무도 안 넘어가고, 너무 충분하면 넘어갈 이유가 없다.**
경계는 「재미있었다, 더 보고 싶다」에 둔다.

## 3. KLifeMap 세션에 필요한 것 (요청 사항)

WikiTip 쪽은 내가 만든다. **KLifeMap 은 남의 프로젝트이므로 직접 만지지 않는다.**
필요한 것은 셋이다.

1. **B2B API 접근** — 엔드포인트 주소, 인증 방식, 발급 키
2. **응답 계약** — 궁합 판정의 외부 필드 이름과 의미.
   그쪽이 `apiBusiness.js` 에서 세운 원칙대로 「내부 이름을 그대로 내보내지 않는」 형태
3. **출생시각 없이 호출 가능한지** — 생년월일만으로 궁합 판정이 나오는지,
   나온다면 정밀도가 어떻게 표기되는지

그리고 하나 확인이 필요하다 — **KLifeMap 에 영문 화면이 있는가.**
없으면 유입을 보내도 거기서 끊긴다. 이게 전환의 병목이 될 수 있다.

## 4. 붐업의 실제 크기 — 산수

동남아 한류 독자에서 KLifeMap 유료 전환까지의 깔때기를 가정해 본다.

```
WikiTip 월 방문         100만
  ↓ 도구 진입률 5%
도구 이용                5만
  ↓ KLifeMap 이동 20%
KLifeMap 방문            1만
  ↓ 유료 전환 2%
결제                     200건 / 월
```

건당 19,900원이면 **월 400만원**이다. 트래픽 100만에 400만원.
광고로만 벌면 그 트래픽으로 월 400만원이 안 나온다(동남아 RPM 기준).
**즉 같은 트래픽에서 KLifeMap 경로가 광고보다 낫다.**

⚠ **위 전환율은 전부 가설이다.** 실제로 재기 전까지 이 숫자를 근거로 삼지 않는다.
다만 방향은 분명하다 — **트래픽을 광고로만 쓰는 것은 낭비다.**

## 6. UTM 규약 — 먼저 정해 둔다

나중에 정하면 초기 유입의 출처를 영영 모른다. 아카이브와 같은 논리다.

```
utm_source=wikitip
utm_medium=article | tool | nav
utm_campaign=<기사 slug 또는 tool 이름>
```

예) `https://klifemap.ai/?utm_source=wikitip&utm_medium=tool&utm_campaign=compatibility`

**KLifeMap 쪽에서 이 파라미터를 집계해 주면** 어느 기사가 결제로 이어졌는지까지 보인다.
그게 되면 「전환되는 기사」를 골라 더 쓸 수 있다. 집계 가능한지 저쪽에 물어 둔다.
