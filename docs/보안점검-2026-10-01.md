## 신한은행은 어떻게 뚫렸나 — 우리가 무엇을 재야 하는가

```
① 본인 확인 절차를 «거치지 않고» 무단 접근  ← 인증 우회
② 조회 입력값을 «무작위로 대입»해 정보 호출  ← 열거·무작위 대입
③ 그렇게 얻은 번호로 다른 정보를 연쇄 탈취
```

⭐ 보안업계 판단 — **신한을 노린 공격이 아니었다.** AI 가 플랫폼 취약점을 무작위로
훑다가 걸린 것이다. 같은 방식으로 강남언니·29CM 도 털렸다.
⇒ **작은 사이트라고 비켜 가지 않는다.** 방문자가 적다는 것은 방어 이유가 못 된다.

### ②를 고치다 더 나온 것 — 자가 헛돌고 있었다

인증번호를 맞추는 쿼리가 `WHERE email = ? AND code = ?` 였다.
**틀린 번호로는 행을 못 찾으니 셀 대상 자체가 없었다** — 횟수를 올리는 코드를
붙여도 영영 안 올라갔을 자리다. 주소로만 찾아 와서 번호를 «코드에서» 맞추도록 고쳤다.

### 셋 다 지킨 원칙

```
✅ 잠겼다는 말을 손님 화면에 내지 않는다
   「잠겼습니다」라고 하면 그 주소에 계정이 있다는 것을 알려 주는 셈이다.
   틀렸을 때와 «똑같은 말»을 낸다
✅ 비밀번호가 «맞아도» 잠긴 동안에는 안 연다 — 안 그러면 잠근 뜻이 없다
✅ 성공하면 바로 푼다 — 멀쩡한 손님을 가두지 않는다
✅ 대소문자·앞뒤 공백을 다듬어 센다 — 안 그러면 「A@b」와 「a@b」로 나눠 두드린다
✅ 한도를 넘겨도 «시간»이 지나면 풀린다 — 영구 차단은 공격자가 남을 가두는 수단이 된다
```

## 2. 재 보고 «괜찮았던 것»

```
라이브 /api/admin/*          401  ✅ 잠겨 있다
라이브 /api/db/customers     401  ✅ 잠겨 있다  ← 신한이 털린 바로 그 자리
라이브 /api/auth/me          401  ✅
브라우저로 나가는 파일 2,299개   비밀값 0곳  ✅
비밀번호 보관                scrypt + 소금 + timingSafeEqual  ✅ (두 서버 모두)
문의·주문 조회 (/api/my/inquiries/:id)   제 것인지 보고 남의 것은 404  ✅
```

⚠ **처음 훑었을 때 15곳이 빨간불이었는데 전부 헛것이었다.**
`window.SAJU_API_KEY = '__SAJU_API_KEY__'` 의 자리표가 마침 16자라 값처럼 보였다
(서버가 내보낼 때 진짜 열쇠로 바꿔 끼운다). **열다섯이 똑같이 걸리면 그건 자가 틀린 것이다** —
자를 고치고 다시 쟀다.

## 3. 남은 것 — 아직 «안 고친» 것

| 급 | 어디 | 무엇 | 왜 오늘 안 했나 |
|---|---|---|---|
| 🟡 | 세 사이트 가입 | `409 account already exists` 로 **그 주소에 계정이 있는지 알 수 있다** | 고치면 이미 가입한 손님이 까닭을 못 듣는다. 로그인 잠금이 붙어 대량 조회는 막혔다 |
| 🟡 | `/v1/keys` | 무료 열쇠를 아무 주소로나 계속 발급받을 수 있다 | 셀프 발급이 이 상품의 설계다. 한도를 거는 쪽으로 따로 본다 |
| 🟡 | `/api/billing/checkout` | 비회원 주문이라 문이 없다. 분당 30회(IP)만 | 게스트 결제는 사장님이 여신 길이다. 쿠폰 쪽은 오늘 막았다 |
| ⬜ | `SAJU_API_KEY` | 운영에 **안 걸려 있다**(라이브에서 확인) | 코드 주석이 이미 「페이지 소스에 노출되므로 자물쇠가 될 수 없다」고 적어 두었다. 효과가 제한적이라 급을 낮춘다 |
| ⬜ | `/api/vote`·`/api/comments` | 같은 사람이 여러 번 넣을 수 있다 | 매출·개인정보가 아니다. 유입 일이 끝난 뒤 본다 |
