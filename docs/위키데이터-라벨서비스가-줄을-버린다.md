# 위키데이터 SPARQL — `SERVICE wikibase:label` 이 **말없이 줄을 버린다**

*2026-09-07 · 5번(K Culture Wire) 실측 · 전 유닛 공용*

사장님 지시(2026-09-04): **「새롭게 확인된 것은 반드시 문서로 작성해 전 유닛에 공유하라」**
이 문서는 그 지시에 따른 것이다. 위키데이터를 쓰는 유닛(1·3·4·5·6번)이 다 걸린다.

---

## Ⅰ. 무엇이 일어났나

### 1-1. 증상 — K팝 팀 표에 에스파가 없었다

`collect-kcw-group-afterlife.mjs` 로 한국 음악 팀 697팀을 받아 열람을 쟀다. 수는 그럴듯했고
자가시험 20가지도 다 통과했다. 그런데 기사에 쓸 이름을 찾다가 **aespa · TXT(Tomorrow X
Together) · RIIZE · BOYNEXTDOOR · BABYMONSTER 가 통째로 없다**는 것을 알았다.

⛔ 수만 보고 넘겼으면 「K팝 팀 697팀을 다 쟀다」는 기사가 그대로 나갔을 것이다.
   에스파가 빠진 K팝 표는 **어느 독자든 첫 줄에서 알아본다.**

### 1-2. 까닭이 둘이었다

```
① 분류를 너무 좁게 잡았다
   ?g wdt:P31/wdt:P279* wd:Q215380   (음악 그룹)
   ⛔ 걸그룹(Q641066)은 Q215380 아래가 «아니다».
      Q641066 의 P279 는 Q2491498 · Q7623897 · Q120544 로만 올라간다.

② ⭐ SERVICE wikibase:label 이 줄을 «버렸다»  ← 이것이 더 무섭다
   같은 조건에서 라벨 서비스만 뺐더니 191 → 318 로 늘었고 에스파가 들어왔다.
   ⛔ 오류도 경고도 없다. 200 이 오고 JSON 이 온다. 그냥 «적게» 온다.
```

### 1-3. 실측 (2026-09-07)

| 질의 | 라벨 서비스 | 받은 항목 | 에스파 |
|---|---|---:|---|
| `P31=Q641066 · P495=Q884 · 영문문서 있음` | **쓴다** | 191 | ✕ 없다 |
| 같은 조건 | **안 쓴다** | 191 | ✅ 있다 |
| `P31=Q641066 · P495=Q884` (영문문서 조건 없이) | 안 쓴다 | **318** | ✅ 있다 |
| 넓힌 분류 넷 + 나라 조건 셋 | 안 쓴다 | **847** | ✅ 있다 |

⚠ 첫 줄과 둘째 줄은 «같은 191» 인데 안에 든 항목이 다르다. **수가 같아도 내용이 다르다.**
  이것이 겉수만 보면 절대 안 드러나는 까닭이다.

## Ⅱ. 그래서 어떻게 쓰나

### 2-1. 라벨 서비스를 쓰지 않는다

```sparql
⛔ 쓰지 말 것
   SERVICE wikibase:label { bd:serviceParam wikibase:language "en" }

✅ 이름은 «영문 위키 제목»에서 꺼낸다 — 어차피 열람을 셀 때 쓰는 열쇠다
   ?en schema:about ?g ; schema:isPartOf <https://en.wikipedia.org/> .
   → decodeURIComponent(en.split('/wiki/')[1]).replace(/_/g,' ')
```

이름이 꼭 라벨이어야 하면 **따로** 받는다 — `wbgetentities` 에 `ids` 를 50개씩 묶어
`props=labels&languages=en` 으로 물으면 빠지는 것 없이 온다.

### 2-2. 분류는 한 개로 좁히지 않는다

```sparql
VALUES ?kind { wd:Q215380 wd:Q2088357 wd:Q641066 wd:Q5741069 }
?g wdt:P31/wdt:P279* ?kind .
```
음악 그룹 · 음악 앙상블 · 걸그룹 · 보이밴드. 넷을 다 넣어야 K팝이 다 들어온다.

### 2-3. 나라 조건도 하나로 좁히지 않는다

```sparql
{ ?g wdt:P495 wd:Q884 } UNION { ?g wdt:P17 wd:Q884 } UNION { ?g wdt:P740/wdt:P17 wd:Q884 }
```
P495(제작국)만 보면 그 속성이 없는 항목이 통째로 빠진다.

### 2-4. ⭐ 받고 나면 **아는 이름으로 검산한다**

이번에 이것 하나가 사고를 막았다. 자가시험은 함수를 시험할 뿐, **우물이 덜 길어 온 것은
못 잡는다.** 그래서 받은 목록에 «반드시 있어야 할 이름»을 넣어 두고 대조한다.

```js
const 반드시 = ['Aespa','BTS','Blackpink','Twice','Stray Kids','Tomorrow X Together','Riize'];
const 없는것 = 반드시.filter((n) => !받은이름.some((x) => x.toLowerCase() === n.toLowerCase()));
if (없는것.length) throw new Error('우물이 덜 길어 왔다 — 빠진 것: ' + 없는것.join(', '));
```

각 유닛이 자기 분야의 「반드시 있어야 할 이름」을 정해 두면 된다 —
6번은 삼성전자·SK하이닉스, 3번은 서울대·연세대, 5번은 위의 K팝 팀들.

## Ⅲ. 그래도 못 잡은 것 — 0 으로 안 채운다

**(G)I-DLE 은 넓힌 질의로도 안 잡힌다.** 위키데이터 항목에 나라 속성(P495·P17·P740)이
아예 없기 때문이다. 이름으로 억지로 끼워 넣지 않고 **「못 잡았다」고 자료와 지면에 적었다.**

⛔ 「거의 다 잡았으니 됐다」로 넘기지 않는다. 못 잡은 이름을 적어 두면 다음 세션이 고칠 수 있다.

## Ⅳ. 이 일이 같은 병의 몇 번째인가

이 저장소에는 같은 꼴의 사고가 이미 여럿 적혀 있다.

```
ctype undeploy    종료코드 0 인데 아무 일도 안 했다
프로필 복사       파일은 생겼는데 본문 51자짜리 빈 껍데기였다
대화록 복사       줄 수 122개인데 사람이 말한 줄은 4개였다
업무보고 PDF      파일 크기는 수백 KB인데 표지 한 장이었다
라벨 서비스       200 이 오고 JSON 이 오는데 줄이 빠져 있다   ← 오늘
```

⭐ 하나로 묶으면 이렇다 — **「받았다」와 「제대로 받았다」는 다른 것이다.**
  겉신호(종료코드·크기·줄 수·응답코드)가 맞으면, 그다음에 **안을 열어 아는 것과 대조한다.**
