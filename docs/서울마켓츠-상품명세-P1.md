### 1-2. ⚠ 두 수가 서로 다른 것을 밝힌다 — 애널리스트 「181」과 「94」

앞선 문서에 181, 아카이브에 94 가 있어 오늘 갈라 봤다. **둘 다 맞고, 다른 것을 센 수다.**

```
181명   보고서 624건의 «작성자» 칸에 나오는 서로 다른 이름 수 (622건에 이름이 붙어 있다)
 94명   한경 «순위표»(analyst/ranking?periodType=1M)에 오른 사람 수
⇒ 상품에는 «181» 을 쓴다. 우리가 파는 것은 순위가 아니라 「누가 무엇을 바꿨나」다
⛔ 두 수를 같은 칸에 쓰지 않는다. 섞이면 「우리 애널리스트 수」가 그때그때 달라진다
```

### 1-2-b. ⚠ People Panel 의 「2,924」와 「2,879」도 다른 수다 — 45행이 빠져 있다

앞선 문서에 2,924 라 적혀 있고 상품 파일은 2,879 행이다. 오늘 갈라 봤다.

```
2,924  DART 고용 원자료의 회사 수 (종목코드가 다 있고 겹치지도 않는다)
2,879  상품 파일의 행 수
   45  빠진 것 — **45곳 전부 종목코드에 «글자»가 들어 있다**
        0068Y0 비엔케이제3호스팩 · 0115H0 삼성스팩13호 · 0030R0 대신밸류리츠 · 0015S0 페스카로 …

⚠ 이 45 는 DART 의 «내부 코드»이고 KRX 6자리 코드가 아니다. 그래서 조인에서 빠졌다.

🔴 **다만 그 안에 리츠가 있다 — 리츠는 실제 상장사다.** 즉 우리가 «있는 상장사»를 놓치고 있다.

```

🔴 리츠는 빼면 안 된다 — 6번 P3 에서 KRX 코드로 다시 붙인다
⛔ 어느 쪽이든 «조용히» 빠지면 안 된다. 상품 사전에 「빠진 45곳」을 이름으로 싣는다

## Ⅱ. 칸 사전 — 어떻게 만들 것인가

### 2-1. 규칙 (People Panel 에서 이미 지킨 것을 전 상품에 넓힌다)

```
✅ 이름에 «단위»를 박는다        annual_pay_per_person_krw_men   (krw · per_person 이 이름에 있다)
✅ 못 준 칸에는 «까닭 칸»을 둔다  pay_ratio_withheld_reason
✅ 사전을 상품과 «함께» 낸다      파일 하나에 표 하나, 사전 하나
⛔ 빈 것을 0 으로 채우지 않는다   빈칸으로 두고, 사전에 「빈칸의 뜻」을 적는다
⛔ 한국어 칸이름을 그대로 내지 않는다 — 손님이 영어권이다
```

### 2-2. 🔴 오늘 겪은 함정 둘 — 상품 지면에도 그대로 걸린다

```
🔴 아카이브 «안쪽» 필드를 지면·상품으로 흘리지 않는다
   /read-in 이 「(봇 제외) · 판별 제목은 …」을 라이브에 띄우고 있었다.
   ⇒ 안쪽 글(한국어)과 손님에게 나가는 글(영어)은 다른 것이다. 함수를 따로 둔다
🔴 사람·회사를 «이름»으로 추리지 않는다
   이름이 같은 다른 것이 묶인다. 실측 — 9,249행이 id 9,249개인데 이름은 8,908개였다
   ⇒ 상품에서는 corp_code(DART)·ticker(KRX) 같은 «번호»로 추린다
```

### 2-3. 상품별 칸 (초안 — 6번 P3·P4 에서 굳힌다)

**Korea Ownership Ledger** — 대량보유 원자료 11칸을 영문화한다.

| 우리 칸 | 원자료 | 비고 |
|---|---|---|
| `filing_id` | 접수번호 | 열쇠. 같은 건이 두 번 들어오는 것을 막는다 |
| `filed_on` | 접수일 | ISO 8601 · KST |
| `filing_kind` | 보고구분 | 영문 사전으로 옮긴다(일반/변동 등) |
| `holder_name` | 보고자 | ⛔ 로마자로 «지어내지» 않는다. 원문이 영문이면 그대로, 아니면 원문+미확인 표시 |
| `shares_held` · `shares_change` | 보유주식수·증감 | 정수 |
| `stake_pct` · `stake_change_pct` | 보유비율·증감 | 소수 |
| `related_party_shares` · `related_party_pct` | 특별관계자 주식수·비율 | |
| `reason_raw_ko` | 보고사유원문 | ⚠ 원문이 한국어다. **영문 요약을 우리가 지어내지 않는다** — 원문 칸으로 둔다 |

**Korea Mezzanine Book** — DART 원문 46칸 가운데 상품에 낼 것을 고른다.

```
✅ 값이 되는 칸   bd_knd(종류) · bd_fta(총액) · cv_prc(전환가) · cv_rt(전환비율) ·
                cvrqpd_bgd/edd(전환청구기간) · act_mktprcfl_cvprc_lwtrsprc(리픽싱 하한) ·
                bd_intr_ex/sf(표면·만기이자) · sbd(청약일) · pymd(납입일)
⚠ 46칸을 다 내지 않는다 — 다 내면 「DART 를 그대로 옮긴 것」이 되어 우리 몫이 없다.
  우리 몫은 «영문화 + 한 표로 모으기 + 판 번호»다
⬜ 못 쟀다 — 46칸 각각의 채움률. P3 에서 6번이 잰다
```

**Korea Consensus Tape** — 13칸 가운데 「바뀐 것」을 축으로 삼는다.

```
✅ report_id · published_on · analyst_name · broker · ticker · sector · rating ·
   target_price · prev_target_price · target_change (우리가 계산: 올림/내림/유지/신규)
⭐ 우리 몫은 target_change 와 analyst_name 축이다 — 값이 아니라 «변경 이력»
⛔ target_change 를 「매수 신호」로 쓰지 않는다. 「iM증권이 X일에 Y원으로 바꿨다」는 사실이다
```

**Korea People Panel** — 이미 22칸으로 낸 것을 그대로 판 번호만 붙인다.

## Ⅲ. 배달 형식

### 3-1. 무엇을 하고 무엇을 안 하나

```
✅ 파일        CSV (모두가 연다) + Parquet (큰 것을 빨리 읽는다)
✅ REST API    읽기 전용 질의 · 열쇠 인증 · 문서 (P6 · 1번·2번·6번)
✅ 판 번호     snapshot 이름에 «만든 날»을 박는다 — korea-people-panel-2026-09-09.csv
🟡 나중        엑셀 플러그인 · HTML 조각
⛔ 안 한다     실시간 시세 · 손님 DB 직결 동기화
```

### 3-2. 판 번호 규칙 — **지난 판을 지우지 않는다**

```
이름        <상품>-<YYYY-MM-DD>.csv  ·  사전은 <상품>-dictionary-<YYYY-MM-DD>.csv
지난 판     남긴다. 손님이 「그때 그 수」를 다시 볼 수 있어야 값이 붙는다
⛔ 조용히 덮어쓰지 않는다 — 오늘 신문 제목 수집기에서 그 결함을 겪었다.
  같은 날 두 번 받으면 «합치는» 것이 맞고, 다른 날은 «따로 두는» 것이 맞다
바뀐 것     판마다 changelog 한 줄 — 행 수 · 칸 수 · 무엇이 바뀌었나
```

### 3-3. 분류 축 — QUICK 의 것을 쓴다 (좋은 축이라 그대로 쓴다)

```
Data Mapping   Ticker-level  ↔  Macro-level
Status         Available · New · Update · Coming Soon
Delivery       REST API · File
Provider       SeoulMarkets — 파트너 칸은 «비워 둔다». 없는 것을 있는 척 안 한다
```
