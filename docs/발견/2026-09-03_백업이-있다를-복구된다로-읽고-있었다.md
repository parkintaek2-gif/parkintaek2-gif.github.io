# 「백업이 있다」를 「복구된다」로 읽고 있었다 — 셋 가운데 하나만 살아난다

발견 2026-09-03 18:1x KST · 5번(총괄대행) · **문서가 16일 동안 거짓을 가리키고 있었다**

> CLAUDE.md 에 이렇게 적혀 있었다 — 「Cloudtype 이 죽으면 **DNS 만 되돌려 복구한다.**
> 그래서 푸시는 항상 양쪽에 한다」

---

## 1부. 결론

우리 복구 계획은 **셋 가운데 하나에만 맞는 말**이었다. 그리고 그 하나조차 **16일 낡아** 있었다.

```
seoulmarkets.com   ✅ 복구된다 — 지면이 뿌리 경로에 있어 정적 파일로 그대로 나간다
kculturewire.com   🔴 복구 안 된다 — /wikitip 접두를 «서버»가 붙인다
100yearmap.com     🔴 복구 안 된다 — /100y 접두를 «서버»가 붙인다
```

⛔ 게다가 그 백업으로 미는 `site` 원격이 **이 저장소 설정에서 아예 빠져 있었다.**
그래서 백업은 **2026-08-18 에서 멈춰 3,834개 커밋(16일)** 뒤처져 있었다.
문서는 「항상 양쪽에 푸시한다」고 적혀 있었는데, **밀 곳이 없었다.**

## 2부. 어떻게 알아챘나 — 우연이다. 그것이 문제다

카드 고아를 고쳐 배포하려고 `git push site main` 을 쳤더니 이렇게 났다.

```
fatal: 'site' does not appear to be a git repository
```

⭐ **아무 검사도 이것을 잡지 못했다.** 배포 관문(`check-deploy-ready.mjs`)은 `origin` 만 본다.
그래서 「✅ 최신이다」로 초록을 냈고, 나는 그 초록을 보고 배포했다.
**배포는 옳게 나갔지만 백업은 16일째 낡은 채였고, 아무도 몰랐다.**

## 3부. 어떻게 쟀나

```
1. 백업이 무엇을 내주나
   curl -s -o /dev/null -w '%{http_code}' https://parkintaek2-gif.github.io/          → 200
   /wikitip/malaysia → 200   ·   /wikitip/ → 404   ·   /100y/ → 404
   /wikitip/weeks-counter → 404 (오늘 낸 지면)

2. 왜 404 인가 — 접두를 «누가» 붙이나
   grep -n "'100yearmap.com'" server.mjs
   → 269~272줄. 손님이 온 «호스트»를 보고 경로 접두를 갈아 끼운다.
   ⛔ GitHub Pages 는 정적 파일만 내주므로 그 갈아끼우기를 못 한다.

3. 백업이 얼마나 낡았나
   curl -s https://api.github.com/repos/parkintaek2-gif/parkintaek2-gif.github.io
   → 마지막 push 2026-08-18T06:31:58Z
   git rev-list --count 98427876..HEAD  → 3,834

4. 밀어도 안전한가 — «조상인지» 먼저 봤다
   git merge-base --is-ancestor 98427876 HEAD   → 참
   ⭐ 조상이면 fast-forward 라 잃는 것이 없다. 이것을 확인하기 «전에» 밀지 않았다.
```

## 4부. 고친 것

```
되살렸다  git remote add site https://github.com/parkintaek2-gif/parkintaek2-gif.github.io.git
밀었다    git push site main  → 98427876..ebe7f05b  (fast-forward, 3,834개 커밋)
고쳤다    CLAUDE.md 백업 절 두 곳 — 「하나만 복구된다」와 그 까닭을 못박음
고쳤다    docs/배포-가이드.md 머리 — 「github.io = 실제 서비스」가 거꾸로임을 못박음
```

⚠ `docs/배포-가이드.md` 는 2026-07-31 자로 **「github.io 가 실제 서비스, seoulmarkets 는 미러」**
라고 적혀 있었다. 지금은 정반대다(Cloudtype 이 낸다). 그 문서를 그대로 따른 세션이 있었다면
백업을 본체로 알고 손댔을 것이다. **지우지 않고 머리에 「낡음」을 붙여 남겼다** —
왜 뒤집혔는지가 다음 사람에게 정보다.

## 5부. 잰 것과 «제 판단»을 갈라 적는다

```
실측    백업 뿌리 200 · /wikitip/malaysia 200 · /wikitip/ 404 · /100y/ 404 · 오늘 지면 404
실측    server.mjs 269~272줄이 호스트로 접두를 갈아 끼운다
실측    백업 마지막 push 2026-08-18T06:31:58Z · 그 사이 커밋 3,834개
실측    `site` 원격이 git config 에 없었다 (git remote -v 에 origin 하나뿐)
실측    98427876 이 HEAD 의 조상이다 → fast-forward 로 밀었고 실제로 그렇게 나갔다

제 판단  「이 백업으로는 KCW·백년지도를 못 살린다」는 제 판단이다.
        ⬜ 접두를 Pages 쪽에서 흉내낼 길(리다이렉트 파일·별 저장소)을 «다 재 보지는 않았다».
        「지금 그대로는 안 된다」까지가 잰 것이고, 「어떤 방법으로도 안 된다」는 아니다.
제 판단  「이것을 잡는 검사가 있어야 한다」도 제 판단이다. 아래 7부에 왜 아직 안 만들었는지 적는다.

⛔ 안 말한 것  Cloudtype 이 실제로 얼마나 자주 죽는지는 모른다. 위험의 «크기»는 안 쟀다.
```

## 6부. ⬜ 못 쟀다

```
⬜ GitHub Pages 가 지금 새 커밋으로 다시 지어졌나 — 밀고 몇 분이 걸린다. 다음 소통에서 잰다
⬜ Cloudtype 이 죽는 빈도 — 기록을 안 뒤졌다. 그래서 이 위험의 «값»을 매기지 못한다
⬜ Pages 에서 호스트 접두를 흉내낼 수 있나 — 위 5부의 판단 그대로, 다 재 보지 않았다
⬜ 다른 저장소(klifemap)에도 같은 백업 구멍이 있나 — 오늘 안 봤다
```

## 7부. 왜 검사를 «아직» 안 만들었나

⭐ 우리 규칙은 「규칙은 문장이 아니라 검사로 둔다」다. 그런데 이 건은 두 가지를 먼저 정해야 한다.

```
1. 「백업이 낡았다」의 문턱을 몇으로 두나 — 매 커밋마다 밀 것인가, 하루 한 번인가
2. 백업을 미는 것을 배포 관문에 «넣을» 것인가 — 넣으면 백업이 죽을 때 배포가 막힌다
```

⛔ 문턱을 안 정하고 검사를 만들면 헛경보를 내고, 헛경보를 내는 자는 꺼진다.
✅ **그래서 오늘은 「재는 법」과 「고친 기록」만 남긴다.** 문턱은 다음 소통에서 6번과 정한다
   (6번이 배포 관문을 함께 만졌다). ⬜ 그때까지 이 자리는 «못 쟀다»가 아니라 **«안 정했다»**다.

## 8부. 다른 유닛이 지금 확인할 것

```
전 유닛  git remote -v 를 쳐 보십시오. `site` 가 있습니까?
         없으면 → git remote add site https://github.com/parkintaek2-gif/parkintaek2-gif.github.io.git
6번      배포 관문이 `origin` 만 봅니다. 백업까지 볼지, 문턱을 어디에 둘지 함께 정합시다
1번·4번  klifemap 에도 백업 경로가 문서에 적혀 있다면 «그것이 정말 되는지» 한 번 재 보십시오
```

⭐ 이 발견의 값은 「백업이 낡았다」가 아니다. **「문서에 적힌 복구 계획을 아무도 재 본 적이 없었다」**는 것이다.
