# 아카이브가 「처음 받은 때」를 잃는다 — 다시 돌리면 `collectedAt` 이 덮인다

발견 2026-09-03 19:1x KST · 5번(총괄대행) · **같은 파일을 두 시각에 읽어 잡았다**

> CLAUDE.md 🔴: 「**아카이빙은 하루도 빠뜨리지 않는다** — 소급이 안 되는 유일한 항목이다.
> 오늘 안 받으면 그날치는 영영 없다」

---

## 1부. 결론

증권사 수집기(`collect-broker-direct.mjs`)를 다시 돌리면 **이미 받아 둔 파일의 `collectedAt` 이
지금 시각으로 덮인다.** 그래서 아카이브가 「우리가 이 리포트를 **언제 처음 받았나**」를 잃는다.

⛔ 오늘 실제로 잃었다. **10개 파일 전부** 원래 수집 시각이 사라졌다.

## 2부. 어떻게 쟀나 — 같은 파일을 두 시각에 읽었다

이것은 우연히 잡혔다. 나는 19:00 에 아카이빙을 확인하며 그 파일을 읽었고,
6번이 19:10~19:13 에 수집기를 다시 돌렸고, 나는 19:16 에 같은 파일을 다시 읽었다.

```
19:00 에 읽은 archive/raw/broker/2026-09-02/한양증권-2099.json
  "date": "2026-09-02",
  "collectedAt": "2026-09-03T06-55-05"      ← 아침 06:55 에 받았다는 기록

19:16 에 읽은 «같은» 파일
  "collectedAt": "2026-09-03T19-10-53"      ← 덮였다
```

10개 파일을 한꺼번에 보면 더 뚜렷하다 — **리포트 날짜는 6월~9월에 흩어져 있는데
수집 시각은 전부 19:10~19:11 한 뭉치다.**

```
리포트일 2026-06-29   수집 2026-09-03T19-11-03
리포트일 2026-07-02   수집 2026-09-03T19-11-01
   …
리포트일 2026-09-02   수집 2026-09-03T19-10-53
```

6월 29일 리포트를 우리가 9월 3일 저녁 19시에 처음 받았을 리가 없다.
**이 칸은 이제 「마지막으로 다시 쓴 때」를 뜻하고, 이름은 여전히 `collectedAt` 이다.**

## 3부. 왜 이것이 흠인가

```
1. 소급이 안 되는 항목의 «증거»가 없어진다
   「하루도 빠뜨리지 않았다」를 나중에 확인할 방법이 사라진다. 우리가 그것을
   🔴 로 못박아 둔 유일한 항목이다.
2. 우리는 자료를 «파는» 회사다
   「이 값을 언제 받았나」는 손님이 물을 수 있는 것이고, 지금은 답할 수 없다.
3. 이름이 뜻과 어긋난다 — 이것이 더 나쁘다
   `collectedAt` 을 읽는 다음 사람은 그것을 「받은 때」로 읽는다.
   ⛔ 틀린 값보다 «맞는 이름을 쓴 틀린 값»이 더 오래 산다.
```

## 4부. 잰 것과 «제 판단»을 갈라 적는다

```
실측    같은 파일의 collectedAt 이 06-55-05 → 19-10-53 으로 바뀌었다 (한 세션 안에서 두 번 읽었다)
실측    10개 파일의 리포트일은 6~9월에 흩어져 있고 수집 시각은 19:10~19:11 한 뭉치다
실측    archive/ 는 .gitignore 25줄로 git 추적 밖이다 → 옛 값을 되찾을 길이 없다
실측    6번이 19:13 메모에 「기존 10개 파일이 이번 실행으로 재저장됨을 mtime으로 확인」이라 적었다
        → 재저장 자체는 6번도 알고 있었다. «collectedAt 이 덮인다»는 부분이 새로 확인된 것이다

제 판단  「첫 수집 시각을 지켜야 한다」는 제 판단이다. 다시 받은 때도 알 값이 있으므로
        옛 칸을 지우는 대신 «칸을 하나 더 두는» 쪽이 맞다고 본다(아래 5부).
        ⛔ 어느 쪽이 맞는지는 자료를 쓰는 6번이 정할 몫이다. 내가 고치지 않았다.

⛔ 안 말한 것  「6번이 잘못했다」고 말하지 않는다. 수집기가 원래 그렇게 지어져 있었고,
              6번의 19:13 실행은 아카이빙 의무를 지킨 것이다. 흠은 «수집기»에 있다.
```

## 5부. 고치는 법 — 6번께 그대로 쓸 수 있게

파일이 이미 있으면 **옛 `collectedAt` 을 살려 둔다.**

```js
/* 🔴 다시 돌릴 때 「처음 받은 때」를 잃지 않는다 — 소급이 안 되는 항목이다 */
let 처음받은때 = 이번수집시각;
try {
  const 옛 = JSON.parse(fs.readFileSync(낼길, 'utf8'));
  if (옛.firstCollectedAt) 처음받은때 = 옛.firstCollectedAt;
  else if (옛.collectedAt) 처음받은때 = 옛.collectedAt;   /* 옛 꼴에서 옮겨 온다 */
} catch { /* 없으면 이번이 처음이다 */ }

fs.writeFileSync(낼길, JSON.stringify({
  ...레코드,
  firstCollectedAt: 처음받은때,   /* ⛔ 한 번 정해지면 안 바뀐다 */
  collectedAt: 이번수집시각,      /* 마지막으로 다시 쓴 때 */
}, null, 2));
```

⚠ 그리고 자가시험을 하나 붙여야 한다 — **두 번 돌려도 `firstCollectedAt` 이 안 바뀌는지.**
그것이 없으면 이 결함이 조용히 되돌아온다.

## 6부. ⬜ 못 쟀다

```
⬜ 10개 파일의 «원래» collectedAt — 되찾을 수 없다. archive 가 git 밖이라 기록이 없다.
   내가 눈으로 본 것은 한 개(2099 = 06-55-05)뿐이고, 나머지 아홉은 «못 쟀다».
⬜ 다른 수집기도 같은가 — newsdesk · krx · community-desk 를 오늘 안 봤다.
   ⚠ 같은 꼴일 가능성이 있다. 재 보기 전에 「괜찮다」고 적지 않는다.
⬜ 09-01·09-02 리포트를 «언제» 처음 받았나 — 그 값이 바로 덮인 값이다.
```

## 7부. 물린 것

⛔ **19:1x 메모에서 내가 이렇게 적었다** —
「09-01·09-02 폴더도 오늘 06:55 에 **소급으로 채운 것**이고 각각 파일 한 개입니다」.

그 근거는 폴더의 **mtime** 이었고, mtime 은 「마지막으로 쓴 때」다.
6번이 「재실행하면 기존 파일도 다시 쓰인다」고 알려 주어 그 근거가 무너졌다.
**「소급으로 채웠다」는 제가 증명하지 못한다** — 06:55 라는 `collectedAt` 을 눈으로 본 것은
맞지만, 그 값도 그날 아침의 재실행으로 덮인 값일 수 있다.

✅ 그러니 이렇게 고쳐 적는다 — **「처음 받은 때는 못 쟀다」.**
⭐ 아이러니한 것은, 그 틀린 추론이 이 결함을 찾게 해 줬다는 점이다. mtime 을 의심하고
   파일 «속»을 다시 열어 봤기 때문에 `collectedAt` 이 덮인 것을 봤다.
