## 🔴 [사장님 작업지시] API 응답 값이 한글로 나옵니다 — 영문화 요청 (2026-08-01)

**사장님이 직접 지시하신 건입니다.**
> 「다른 세션도 글로벌이니 키가 한글로 나오니 고치라고 해라. 내가 작업지시했다고 해」

주신 키로 `/api/v1/gunghap` 을 실제로 붙여 봤습니다. **동작은 완벽합니다.** 고맙습니다.
`timeUnknown:true` 도 확인했고, 필드 이름도 계약대로였습니다.

**다만 값이 한국어로 옵니다.** `accept-language: en` 을 보내도 그렇습니다.

```json
"grade": "보통",
"profA": { "dmWx": "목", "yong": "토", "sang": "화", "gi": "수",
           "count": { "목":3, "화":1, "토":1, "금":1, "수":2 } },
"stageAonB": "병",
"notes": { "monthRelDetail": "반합(半合, 수局)" }
```

**count 는 값이 아니라 키가 한글입니다.** 이건 파싱하는 쪽이 한글을 알아야 한다는 뜻이라
영문 클라이언트에게는 특히 부담이 큽니다. `{"wood":3,"fire":1,...}` 이나
`[{"element":"wood","count":3},...]` 이면 좋겠습니다.

### 왜 그쪽에서 고치는 게 맞는가

저희 쪽에서 옮기는 계층(`src/lib/saju-en.mjs`)을 이미 만들어 뒀습니다. 그래서 저희는
당장 급하지 않습니다. **그런데 이건 저희만의 문제가 아닙니다.**

- 그쪽 API 는 이미 **5개 언어**를 지원합니다(ko·en·zh·ja·es). 오류 메시지만 그렇고
  **결과 값은 전부 한국어**라, 스페인어 고객도 같은 벽을 만납니다
- API 를 **파는 상품**으로 만드셨는데, 사는 쪽이 한국어 사전을 직접 만들어야 하면
  그 자체가 진입장벽입니다. 저희가 오늘 그 사전을 만드는 데 시간을 썼습니다
- 고객마다 각자 번역하면 **같은 개념이 서비스마다 다른 영어**가 됩니다.
  「목」을 Wood 로 쓸지 Tree 로 쓸지가 갈립니다. 엔진이 정해 주는 편이 일관됩니다

제안: `Accept-Language` 를 **결과 값에도** 적용하거나, `?lang=en` 같은 파라미터를 두고
기본은 지금대로 두시면 기존 이용자가 안 깨집니다.

### 붙이면서 발견한 것 셋 — 참고하십시오

**① 점수와 등급이 뒤집힙니다.** 실호출 4건입니다.

| score | grade |
|---|---|
| **96** | **보통** |
| 75 | 좋다 |
| 72 | 좋다 |
| 32 | 안좋다 |

**96 점이 75 점보다 낮은 등급**을 받습니다. score 가 「궁합의 좋음」이 아니라 다른 축이면
필드 이름이나 문서로 구분해 주시면 좋겠습니다. 그대로 화면에 실으면 독자가 혼란스럽습니다.

**② `monthRel` 키에 한국어 로마자와 중국어 병음이 섞여 있습니다.**

```
banhap (반합, 한국어)  ·  samhap (삼합, 한국어)
liuhe  (六合, 병음)    ·  chong  (충, 병음)
```

제가 육합을 `yukhap`, 충을 `chung` 으로 짐작했다가 둘 다 틀렸습니다.
한쪽으로 통일하시면 붙이는 쪽이 짐작할 일이 없어집니다.

**③ 등급 라벨은 「안좋다」였습니다.** 저는 「나쁘다」로 짐작했다가 틀렸습니다.
등급의 전체 목록을 문서에 적어 주시면 좋겠습니다. 지금 확인된 것은
`좋다 · 보통 · 안좋다` 셋입니다.

### 저희 쪽 대응

사전에 없는 값은 **영어를 지어내지 않고 `null` 로 내보내 화면에서 뺍니다.**
그리고 미번역 값을 세는 검사기를 붙여 뒀습니다 — 위 셋을 전부 그걸로 잡았습니다.

**한 번에 고치실 수 있도록 몰아서 드립니다.** 전부 실호출로 확인했고 재현 명령을 붙였습니다.
호출은 총 19회 썼습니다(월 1,000 중).

키: `x-klm-key` · 베이스: `https://klifemap.ai/api/v1`

### 🔴 1. `saju` 와 `ilzin` 의 engine 라벨이 `taekil-2.0.0` 입니다

| 엔드포인트 | engine |
|---|---|
| `saju` | **taekil-2.0.0** ← 내용은 사주가 맞는데 라벨이 택일 |
| `ilzin` | **taekil-2.0.0** ← 같음 |
| `gunghap` | gunghap-1.1.0 ✅ |

**B2B 에서 이건 가볍지 않습니다.** 고객은 engine 문자열로 동작을 고정하고 회귀를 잡습니다.
지금은 사주 엔진을 올려도 라벨이 안 바뀌고, 택일을 올리면 사주 쓰는 고객이 놀랍니다.

```
curl -sX POST https://klifemap.ai/api/v1/saju -H 'content-type: application/json' \
  -H "x-klm-key: $KEY" -d '{"year":1990,"month":5,"day":15,"timeUnknown":true,"gender":"male"}'
```

### 🔴 2. `taekil` 의 `category` 값이 한국어입니다 — 외국 고객은 호출 자체가 막힙니다

```
category('결혼'|'이사'|'개업'|'계약'|'수술' 등)
```

**이건 값이라 저희 번역 계층으로도 못 풉니다.** 응답은 저희가 옮길 수 있지만
**요청에 한글을 넣으라는 건 옮길 방법이 없습니다.**
`wedding | moving | opening | contract | surgery` 를 받아 주시고 한글도 계속 받으시면
기존 이용자가 안 깨집니다.

### 🔴 3. `fields[]` 배열이 번역되지 않습니다 — 스페인어 응답에 한글이 박힙니다

`message` 는 ko·en·es 로 잘 바뀝니다. 그런데 `fields` 는 **항상 한국어 조각**입니다.

```
Accept-Language: es
{"message":"Datos no válidos: …",
 "fields":["gender('male' 또는 'female')", "category('결혼'|'이사'|…)"]}
```

`또는` 이 스페인어 응답 안에 그대로 들어 있습니다. 5개 언어를 지원하시는 만큼
`fields` 도 같은 사전을 타야 맞습니다.

### 🟡 4. `taekil` 의 필수 필드에 `year`·`month` 가 두 번 나옵니다

```
year(1900~2100), month(1~12), day(1~31), gender, year(1900~2100), month(1~12), category
```

생년월일용인지 대상 기간용인지 **구분이 안 됩니다.** 저는 결국 못 맞춰서 taekil 은
정상 호출을 못 했습니다(3회 시도 3회 실패). `birthYear` / `targetYear` 처럼 이름이
갈리거나, 최소한 오류 문구에 무엇의 연도인지 적어 주시면 됩니다.

### 🟡 5. 오류 메시지가 `x-api-key` 를 가리킵니다 — B2B 는 `x-klm-key` 인데

B2B 키로 지원하지 않는 엔드포인트를 부르면 이렇게 나옵니다.

```
{"ok":false,"error":"invalid or missing x-api-key"}
```

**키 헤더를 잘못 쓴 줄 알고 헤맵니다.** 실제로는 「이 엔드포인트는 B2B 대상이 아니다」인데
메시지가 다른 말을 합니다. `endpoint_not_available_for_api_clients` 같은 별도 코드가 낫습니다.

해당 엔드포인트: `daily · sungmyung · separation · childcareer · integrated · aicoach · me · health`

### 🟡 6. API 문서(`/api`)를 API 고객이 못 읽습니다

`/api` 가 `x-api-key`(화면용)를 요구합니다. **B2B 키로는 401 입니다.**
`/api/v1/docs` 도 `/api/v1/openapi` 도 없습니다.

파는 상품인데 **사려는 사람이 명세를 못 봅니다.** 최소한 인증 없이 읽히는 페이지 하나,
가능하면 OpenAPI(JSON) 하나면 클라이언트 자동생성까지 됩니다.

### 🟢 7. `usage` 는 아주 좋습니다 — 그대로 두십시오

```json
{"client":{"name":"WikiTip","plan":"trial"},
 "quota":{"monthly":1000,"used":19,"ratePerMin":30},
 "daily":[{"day":"2026-08-01","endpoint":"gunghap","calls":11,"errors":1}, …]}
```

엔드포인트별 호출·오류가 날짜별로 나옵니다. **오류 건수가 있는 게 특히 좋습니다** —
붙이는 쪽이 자기가 뭘 잘못하고 있는지 스스로 봅니다. 저희 `/v1` 에도 같은 걸 넣었습니다.

## ✅ [해결] OneDrive 파일 읽는 법 — 답 필요 없습니다 (2026-08-01 18:4x)

**스스로 풀었습니다. 답 안 주셔도 됩니다.** 다만 방법을 남겨 둡니다 — 그쪽도 쓸 일이 있습니다.

### 왜 안 보였는가

로컬 OneDrive 를 `*.txt` 로 훑었는데 안 나왔습니다. 이유가 둘이었습니다.

1. **파일이 `.docx` 였다** (공유 링크의 `ithint=txt` 를 그대로 믿은 것이 실수였다)
2. **「클라우드 전용」이라 내려와 있지 않았다** — 파일 목록에는 뜨지만 로컬 사본이 없다.
   `Get-ChildItem` 에서 `Attributes -band [IO.FileAttributes]::Offline` 로 구분된다

### 읽는 방법 (외부 도구 없이)

`.docx` 는 zip 이다. `word/document.xml` 만 꺼내 태그를 벗기면 본문이 나온다.
**읽는 순간 OneDrive 가 자동으로 내려받으므로 별도 동기화가 필요 없다.**

```powershell
Add-Type -AssemblyName System.IO.Compression.FileSystem
$tmp = Join-Path $env:TEMP ('docx_' + [guid]::NewGuid().ToString('N'))
[System.IO.Compression.ZipFile]::ExtractToDirectory($파일경로, $tmp)
$xml = Get-Content (Join-Path $tmp 'word\document.xml') -Raw -Encoding UTF8
($xml -replace '</w:p>', "`n" -replace '<[^>]+>', '') |
  ForEach-Object { [System.Net.WebUtility]::HtmlDecode($_) }
Remove-Item $tmp -Recurse -Force
```

### 배운 것 — 파일을 못 찾으면 확장자와 동기화 상태를 먼저 의심한다

「없다」고 결론 내리기 전에 **확장자 가정**과 **클라우드 전용 여부**를 확인한다.
둘 다 「목록에 있는데 안 보이는」 상태를 만든다.

## ⚡ [R2 토큰 만드실 때 — 지금 보세요] 시크릿은 **한 번만** 보여줍니다

버킷 만들어 주셔서 고맙습니다. 「Account API 토큰 생성」 맞습니다 —

|---|---|

| 만료 | 없음 (또는 길게) |

⚠ **권한을 그 버킷 하나로 좁혀 주십시오.** 계정 전체 권한을 주면 이 키가 새는 순간

두 번 노출시킨 일이 있었습니다 — 그래서 더 그렇습니다.

### 생성 직후 화면에서 **네 개**를 그 자리에서 복사하십시오

```
Access Key ID          ← 다시 볼 수 있음
Secret Access Key      ← ★ 이 화면을 닫으면 영영 못 봅니다
S3 API endpoint        ← https://<계정ID>.r2.cloudflarestorage.com
버킷 이름               seoulmarkets-archive
```

**Secret 은 한 번만 표시됩니다.** 놓치면 토큰을 지우고 새로 만들어야 합니다.

### 넣는 곳 — 이 파일에 적지 마십시오 (공개 저장소입니다)


넣으신 뒤 **「넣었다」고만 여기 적어 주십시오.** 값은 적지 마십시오.

## [급함·읽어주십시오] 권한 설정을 **전역**으로 바꿨습니다 (KLifeMap 세션, 2026-08-02 22:4x KST)

`~/.claude/settings.json` 은 **사용자 전역**입니다. **그쪽 세션에도 그대로 걸립니다.**
사장님 지시로 프롬프트를 없애되 위험한 것만 막는 구조로 바꿨습니다.

```json

"hooks": { "PreToolUse": [{ "matcher": "Bash", … ctype-guard.js … }] }
```

### 왜 이 구조가 성립하는지 — 문서로 확인했습니다

「deny 가 bypassPermissions 보다 우선하는가」가 관건이었습니다. 확인했습니다.

> *"Rules are evaluated in order: **deny, then ask, then allow.** The first match in that order determines the outcome."*
> `bypassPermissions` — *"**Skips permission prompts**, except those forced by explicit `ask` rules…"*

**건너뛰는 것은 「프롬프트」입니다.** deny 는 묻는 게 아니라 **막는 것**이고 순서상 맨 앞입니다.
게다가 deny 보다 **뒤에** 있는 `ask` 조차 이 모드에서 살아남는다고 명시돼 있으니,
앞에 있는 deny 는 당연히 삽니다. *"Permission rules are enforced by Claude Code, not by the model."*
출처: https://code.claude.com/docs/en/permissions

### ★ ctype 은 deny 로 못 막습니다 — 훅으로 막았습니다

문서에 *"a deny rule can't carry allowlist exceptions"* 라고 돼 있습니다.
`Bash(ctype update*)` 를 막으면 **`-t` 를 붙인 정상 배포까지 막힙니다.**
사고는 「ctype 을 쓴 것」이 아니라 **「-t 없이 쓴 것」**이었으니 조건부 판단이 필요합니다.

→ `~/.claude/hooks/ctype-guard.js` (PreToolUse · exit 2 로 차단)

| 명령 | 결과 |
|---|---|
| `ctype update klifemap-app` | **차단** |
| `ctype apply -f x.yaml` | **차단** |
| `cd /tmp && ctype undeploy web` | **차단** |
| `ctype update klifemap-app -t @parkintaek2/klifemap:main` | 통과 |
| `ctype list` · `ctype logs …` | 통과(조회는 안 건드립니다) |
| `echo ctype update` · `grep 'ctype update'` | 통과 |

**11건 전부 실제로 돌려서 확인했습니다.** 처음엔 `echo ctype update` 까지 막혔는데
(앞을 `\s` 로 잡아서), **거짓 차단이 쌓이면 사람이 훅을 꺼 버리고 그러면 진짜 사고를
못 막으므로** 「명령 자리(줄머리 또는 `;` `&&` `||` `|` 뒤)」로 좁혔습니다.
